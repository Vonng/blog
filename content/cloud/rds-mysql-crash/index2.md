一位读者给我发来两次 RDS MySQL 主备切换的告警短信、
一份第一次事故后的书面答复，以及几张监控截图。

材料里最值得注意的一句话来自阿里云支持：
后台采集会查询 `information_schema.innodb_trx`，
在高并发下可能进一步阻塞 DML，最终因连续三次探活失败触发切换。

答复还说，预计在 7 月 24 日晚关闭这项采集。
四天后，同一个实例再次发生主备切换。

故事到这里很容易写成一句痛快话：
“监控把数据库查挂了，答应关掉，结果又挂了一次。”

但这句话把两层事实混在了一起。
第一次事故有书面归因；
第二次只有相似症状，正式故障报告截至发稿仍未出具。
我们可以追问整改有没有闭环，
却还不能把第二次事故直接判成同一个根因。

这条边界，正是本文的起点。

> **先把材料边界说清楚**
>
> 可以确认的是：投稿材料显示，同一实例在 7 月 23 日和 7 月 28 日发生过两次主备切换；
> 第一次事故后的书面答复，把后台事务采集、`INNODB_TRX` 查询变慢、
> DML 阻塞、探活失败和切换写进了同一条因果链；
> 答复称预计在 7 月 24 日晚关闭该功能。
>
> 目前不能确认的是：关闭动作最终有没有执行、执行到了哪些节点、如何验收；
> 第二次事故是否仍由该采集触发；
> 线上 AliSQL 的对应代码是否与 MySQL 社区版完全一致；
> 以及这项采集在其他实例上的部署范围。
>
> 本文中的曲线读数来自投稿人提供的截图，尚未通过云平台后台独立复核。
> 技术分析用于解释一种与书面答复相符的机制，不代替第二次事故的正式根因报告。

**利益关系说明：**
作者维护开源数据库平台 Pigsty，
对云数据库与自建方案有明确立场。
本文讨论的是一次事故材料与工程原则，不是对 RDS 与 Pigsty 的产品对比测试。

## 太长不看

- 投稿材料显示，一台 32 核 128 GB 的 RDS MySQL 实例，
  在 7 月 23 日和 7 月 28 日各发生一次主备切换。
- 第一次事故后的书面答复明确提到：
  后台采集查询 `information_schema.innodb_trx`，
  高并发下可能进一步阻塞 DML，并因连续三次探活失败触发切换。
- MySQL 社区版源码显示，`INNODB_TRX` 的快照采集路径持有锁系统的全局排他闩锁，
  并遍历事务列表。
  MySQL 官方手册也提醒，过于频繁地采集事务与锁信息会影响其他用户感知到的性能。
- MySQL 8.0.40 重构的是 Performance Schema 的
  `data_locks` 与 `data_lock_waits`。
  在我核对的 8.0.32、8.0.40 和 8.4.3 社区版源码中，
  `INNODB_TRX` 对应路径上的全局排他闩锁仍然存在。
- 阿里云 RDS 使用独立的 AliSQL 分支。
  社区版源码能说明机制与风险，不能证明线上内核逐行相同。
- 第二次事故的正式根因仍然未知。
  现在能够批评的，是整改缺少客户可见的执行与验收闭环；
  不能直接断言阿里云“根本没关”或者“同一个问题再次复发”。

## 先说结论：监控不能改变被监控的对象

这句话听起来像常识，
但要把它做成工程事实，需要付出实现成本。

我自己主要做 PostgreSQL。
数据库不同，监控的基本原则却差不多：
**监控应该帮助维护系统，而不是成为系统新的故障源。**

做 Pigsty 监控时，我给自己定过三条规则。
它们不是行业标准，只是我在生产环境里愿意接受的取舍。

**第一，常规采集周期以 10 秒为主。**
更密的采样当然更好看，
但生产数据库不是为了给监控曲线提供高帧率素材。

**第二，每条监控查询都要有真正能够中止服务端执行的截止时间。**
客户端自己超时退出，却把查询留在数据库里继续跑，
不算完成了超时保护。

**第三，一个采集周期不能无限叠到下一个周期。**
无论采用串行预算、并发上限还是熔断机制，
最坏情况下都应该允许这一轮少几个点，
而不是让采集任务越积越多。

说到底，监控首先要遵守一条很朴素的优先级：
宁可少拿一点数据，也不要为了观察数据库而改变数据库的命运。

## 一、7 月 23 日 09:52

投稿材料里的实例配置是 MySQL 8.0、独享型、32 核 128 GB，
最大 IOPS 60000。
内核小版本为 `rds_20250731`，
小版本升级策略设为手动升级。

<!-- 待补图片：实例配置信息。 -->

根据投稿人提供的监控截图，
当天上午大致经历了下面这段过程：

- 日常会话数约为 1950，连接数利用率不到 5%；
- 08:50 前后，会话数一度升到约 2400，随后回落；
- 09:45 后，活跃会话升到约 250，
  元数据锁等待出现，QPS 峰值接近 2 万；
- 09:52 左右，会话曲线从约 2000 快速降到 570，
  与大量连接在主备切换时被重置的现象相符。

活跃会话数明显高于 32 个 vCPU，
说明当时存在较多排队或等待，
但仅凭这个比值不能判断 CPU 已经“超卖八倍”。

<!-- 待补图片：7 月 23 日会话连接、连接数利用率与 TPS/QPS 曲线。 -->

切换之后，会话数大约用了四十分钟才恢复到 1600 左右，
QPS 也在一段时间内低于切换前。

告警短信写的是“当前已经恢复正常”。
客户随后询问原因，
收到的书面答复如下（原文语病照录）：

> RDS 后台有一个对于数据库活动事务信息采集监控的功能，会查询 MySQL 系统视图
> `information_schema.innodb_trx`。你们实例上的并发事务很高时，
> 锁竞争会阻塞系统视图 `information_schema.innodb_trx` 的查询，
> 而系统视图查询的变慢又会进一步阻塞数据库中的 DML 操作，
> 产生偶发性的实例 hang 住了，后续实例 HA 探活失败，
> 并导致出现连续 3 次实例探活失败触发切换的等情况。

这份答复至少明确了三件事：

1. 平台侧存在查询 `INNODB_TRX` 的后台采集；
2. 答复认为这项采集在高并发下会进一步阻塞 DML；
3. HA 在连续三次探活失败后触发了切换。

换句话说，
平台侧采集不是本文凭曲线猜出来的嫌疑人，
而是被阿里云支持的答复直接写进了第一次事故因果链。

不过，这份答复没有给出采集周期、查询耗时、超时设置、
调用账号、执行日志和当时的锁等待数据。
它解释了“可能如何发生”，
还没有把整条链路变成一份可以复核的事故报告。

## 二、为什么“看一眼”也可能很贵

`information_schema.innodb_trx` 看起来像一张普通表，
实际返回的是 InnoDB 当前事务状态的快照。

在 MySQL 社区版 8.4.3 的
[`storage/innobase/trx/trx0i_s.cc`](https://github.com/mysql/mysql-server/blob/mysql-8.4.3/storage/innobase/trx/trx0i_s.cc)
里，关键路径是这样的：

```cpp
int trx_i_s_possibly_fetch_data_into_cache(trx_i_s_cache_t *cache)
{
  if (!can_cache_be_updated(cache)) {
    return (1);
  }
  {
    /* We need to read trx_sys and record/table lock queues */
    locksys::Global_exclusive_latch_guard guard{UT_LOCATION_HERE};
    trx_sys_mutex_enter();
    fetch_data_into_cache(cache);
    trx_sys_mutex_exit();
  }
  return (0);
}
```

这里最值得注意的是
`Global_exclusive_latch_guard`：
采集过程持有锁系统的全局排他闩锁，
随后再持有 `trx_sys` mutex，
然后构建事务信息缓存。

### 这段时间里做了什么

`fetch_data_into_cache()` 会访问
`trx_sys->rw_trx_list` 和 `trx_sys->mysql_trx_list`。
循环会跳过尚未启动的事务，
但仍需逐项检查列表中的事务对象，
并为需要输出的事务读取状态。

其中包括：

```cpp
char query[TRX_I_S_TRX_QUERY_MAX_LEN + 1];
stmt_len = innobase_get_stmt_safe(trx->mysql_thd, query, sizeof(query));
```

代码还会读取事务持有的锁结构、锁住的表和行数等信息。
因此，采集成本会随着需要遍历的事务对象、
活跃事务及其锁状态增加。

这足以说明风险方向，
但没有运行时剖析数据，
就不应该把一次采集严格写成某个简单的 `O(N)` 公式，
也不能仅凭 1950 个连接推导出它一定耗时多少。

### 100 毫秒缓存不是采集限流

[MySQL 5.7 官方手册](https://dev.mysql.com/doc/refman/5.7/en/innodb-information-schema-internal-data.html)
解释过这套快照机制：
事务与锁信息会放进一个中间缓存，
距离上次读取不超过 0.1 秒时复用同一份快照，
主要是为了让相关视图的 JOIN 保持一致。

同一页手册也明确提醒：
InnoDB 收集这些信息时必须短暂停顿，
过于频繁地查询会影响其他用户感知到的性能。

所以，100 毫秒是快照一致性窗口，
不是给周期性采集准备的安全阀。
一秒、五秒或十秒一次的轮询，
通常仍会触发新的快照采集。

### 8.0.40 修了什么，没修什么

[MySQL 8.0.40 发布说明](https://dev.mysql.com/doc/relnotes/mysql/8.0/en/news-8-0-40.html)
写得很清楚：
这一版重新设计了 Performance Schema 的
`data_locks` 和 `data_lock_waits`，
查询它们不再需要事务系统或锁系统上的全局排他 mutex。

这是重要改进，
但发布说明说的是 Performance Schema 的两张锁表，
不是 `INFORMATION_SCHEMA.INNODB_TRX`。

我分别核对了社区版
[8.0.32](https://github.com/mysql/mysql-server/blob/mysql-8.0.32/storage/innobase/trx/trx0i_s.cc)、
[8.0.40](https://github.com/mysql/mysql-server/blob/mysql-8.0.40/storage/innobase/trx/trx0i_s.cc)
和
[8.4.3](https://github.com/mysql/mysql-server/blob/mysql-8.4.3/storage/innobase/trx/trx0i_s.cc)：
文件当然有其他变化，
但 `INNODB_TRX` 这条路径上的
`Global_exclusive_latch_guard` 仍然存在。

这里也必须同时写出另一半事实：
[阿里云官方文档](https://help.aliyun.com/zh/rds/apsaradb-rds-for-mysql/overview-of-alisql-features)
说明 RDS MySQL 使用深度定制的独立 AliSQL 分支。

因此，社区版源码能证明这种机制真实存在，
也能解释第一次书面答复为什么在技术上说得通；
但 AliSQL 是否修改过这条路径、线上版本具体如何实现，
只有阿里云能够给出确定答案。

更稳妥的结论不是“线上代码肯定一模一样”，
而是：
**第一次书面答复指向了一条在社区基线中确实具有高并发风险的采集路径。**

## 三、7 月 28 日 17:19

四天后，
同一个实例再次发出主备切换告警。

投稿人提供的曲线显示：

- 17:13 前后，InnoDB 脏页从约 9.5 万升到 10 万；
- 17:14:30 左右，脏页指标快速降为 0，
  此后约十五分钟只有零星采集点；
- 17:15:45 和 17:20:45 左右，
  刷盘次数分别出现约 590 和 535 的峰值；
- 17:29:30 前后，脏页指标重新开始上升。

<!-- 待补图片：7 月 28 日 InnoDB Buffer Pool 脏块与刷盘次数曲线。 -->

这组图很像实例失去响应、采集中断，
随后在切换或重启后重新预热；
但“很像”不是“已经证明”。

脏页指标归零还可能来自指标重置、采集端切换、
新节点口径变化或其他我们看不到的平台行为。
仅凭这张图，不能在“刷干净了”“实例重启了”
和“监控暂时采不到了”之间作出唯一判断。

投稿人结合业务侧感受，
把影响窗口估计为 17:14 到 17:29 左右。
这个估计需要业务错误率、连接失败和请求延迟等数据进一步佐证，
不宜只靠数据库监控图下结论。

### 15.7% IOPS 能说明什么

故障期间，截图里的 IOPS 使用率峰值约为 15.7%。
这说明存储配额没有被打满，
却不能单独证明数据库为什么没有更快地刷脏页。

`innodb_io_capacity` 与 `innodb_io_capacity_max`
确实会影响 InnoDB 后台刷盘。
但要把它们列为事故原因，
至少需要事故时的实际参数值、脏页比例、
checkpoint age、page cleaner 状态和写入负载。
这些材料目前都没有。

而且，[阿里云参数文档](https://help.aliyun.com/zh/rds/apsaradb-rds-for-mysql/optimize-the-parameters-of-an-apsaradb-rds-for-mysql-instance)
把 `innodb_io_capacity` 列为可调参数，
给出的建议值是 20000；
[实例参数文档](https://help.aliyun.com/zh/rds/apsaradb-rds-for-mysql/modify-the-parameters-of-an-apsaradb-rds-for-mysql-instance)
也说明用户可以在控制台或 API 中修改开放出来的参数。

所以，“默认参数过于保守”可以作为排查方向，
不能在缺少实际参数值时写成第二次事故的既定根因，
更不能据此断言用户完全没有调节能力。

## 四、“预计今晚可以完成”

第一次事故后的改进方案原文是：

> 以上监控功能绝大部份情况下不会对实例性能造成明显影响，
> 但在实例并发事务数很高的情况下可能遇到，
> 我们可以对客户实例设置关闭此项功能，预计今晚（7 月 24 日）可以完成，
> 关闭操作的执行对客户实例使用无影响。

这里最重要的不是“预计”两个字本身，
而是这份材料里没有后续的执行回执和验收结果。

必须公平地说：
**没有看到回执，不等于可以证明动作没有执行。**
它只能证明，客户手里的沟通记录没有完成下面这条闭环：

```text
提出措施 → 执行动作 → 验证生效 → 告知客户
```

四天后再次发生相似症状，
客户自然会怀疑第一次整改是否生效。
但要回答这个问题，
需要的不是更多修辞，而是几份很具体的记录：

1. 关闭动作何时执行，目标是哪个实例、哪个节点、哪项采集？
2. 执行后用什么方式验证，验证结果是什么？
3. 7 月 28 日的正式根因与 7 月 23 日相同还是不同？
4. 如果这是通用采集功能，平台对其他实例采取了什么风险控制？

在这些问题得到回答之前，
有两句话都不严谨：

- “他们肯定没有关”——证据不足；
- “他们已经关了，所以第二次一定是别的问题”——同样证据不足。

现在可以成立的批评只有一条：
**从客户能够看到的材料出发，这项整改没有形成可验证、可追踪的闭环。**

这已经足够值得重视，
不需要把未知部分写成定论。

## 五、一个容易被忽略的变更通道

这个实例的小版本升级策略设为手动升级。
客户想表达的态度很清楚：
数据库内核不要在未经确认的情况下自动变更。

但托管数据库里，
内核升级并不是唯一的变更通道。
平台侧的监控、巡检、HA agent、代理和管控服务，
可以独立于用户选择的内核升级策略演进。

第一次书面答复本身就说明，
至少有一项平台侧采集会主动查询客户实例。
至于它何时上线、由哪个产品模块负责、
采集周期和超时如何配置，
投稿材料里没有答案。

这并不自动意味着平台做错了什么。
托管服务之所以有价值，
本来就是因为供应商可以在后台统一运维。

问题在于，
当后台动作可能进入数据库的关键锁路径时，
客户是否有权知道它的存在、影响边界和关闭状态？
如果它被列为事故整改项，
客户又如何验证整改已经生效？

手动内核升级控制的是一条看得见的变更通道。
这个案例提醒我们，
托管服务真正需要讨论的，
还有那些客户看不见、却可能影响运行状态的通道。

## 六、HA 是止损，还是放大器

投稿人有一句话很关键：

> 实际上业务还在跑的只是慢，但是他们最近上的新监控，
> 检测状态导致更慢，然后触发了主从切换。

按第一次书面答复描述的链路，
业务先出现高并发和卡顿，
后台采集进一步增加阻塞，
随后连续三次探活失败，触发主备切换。

从用户侧看，
切换会重置大量连接，
连接池重新建连，
新主也可能经历缓存预热。
因此，一次原本还能返回部分请求的降级，
有可能在切换瞬间变成更明显的中断。

但这里也要替 HA 说句公道话。

如果旧主已经持续失去响应，
或者平台判断它即将彻底不可用，
切换到备节点可能正是最合理的止损动作。
没有探活细节、主备状态和业务错误率，
本文无法证明“这次不切一定更好”。

真正值得追问的不是“为什么要 HA”，
而是：

- 探针能否区分“变慢”“锁系统暂时阻塞”和“进程已经死亡”？
- 连续三次失败分别间隔多久，是否结合了多个独立信号？
- 切换前有没有判断备节点是否更健康？
- 切换后有没有验证错误率、延迟和连接恢复速度确实改善？

[阿里云文档](https://help.aliyun.com/zh/rds/apsaradb-rds-for-mysql/manage-primary-secondary-switchovers/)
说明，当主节点异常无法使用或存在潜在风险时，
RDS 会自动触发主备切换。
这解释了机制的目的，
但无法替代对某一次具体切换效果的复盘。

高可用不是“切了就算成功”。
它最终仍要回答一个朴素的问题：
切换以后，用户实际承受的故障时间是缩短了，还是变长了？

---

## 七、如无影响，请忽略

最后回头看那条告警短信：

> 您的云数据库 RDS 的 1 个实例因实例异常（实例 Hang）原因触发并完成主备故障切换，
> 当前已经恢复正常。
> 请检查程序连接是否正常，如无影响请忽略。

作为一条自动告警，
这段话的任务是快速通知客户发生了切换，
不可能在短信里塞下一份完整复盘。

“请检查程序连接是否正常”也没有错。
数据库恢复服务，不等于应用连接池、上游重试和业务状态已经恢复。
最终影响确实需要客户从业务侧确认。

问题出现在另一层：
如果告警之后没有清晰的执行回执和正式根因，
“当前已经恢复正常”就只描述了平台此刻的状态；
它回答不了此前影响了多久、为什么发生、整改是否生效。

所以我现在对“如无影响，请忽略”的理解，
没有最初那么生气，反而更简单：

**它适合结束一条告警，不适合结束一次事故。**

事故要真正结束，
还需要根因、措施、验证和回执。

## 尾声：交出去的是复杂性，留下的是后果

说句公道话，
这不是“云数据库都不行”的故事。

托管数据库接走了大量部署、备份、升级、监控和高可用工作，
这是实实在在的价值。
自建系统换来更多可见性和控制权，
同时也把值班、演练、升级和事故责任重新接回自己手里。
两边都不是免费的午餐。

这个案例真正值得留下的提醒是：

**你可以把复杂性交给供应商，
但业务后果不会跟着一起转移。**

因此，托管服务除了替客户执行操作，
还需要提供足够的可验证性：
什么动作触发了，为什么触发，改了什么，
怎么确认已经生效。

对客户来说，
这不是为了事后找人背锅，
而是为了判断风险是否还在、
下一次高峰能不能放心到来。

对平台来说，
一份边界清楚、证据完整的复盘，
也比一句泛化的道歉更能保护自己。
它能把已知事实、工程判断和未决问题分开，
避免客户只能用下一次事故来验证上一次整改。

透明并不是高可用的附属品。
在托管服务里，
它本来就是可用性的一部分。

## 附：四条更实用的规矩

**一、监控查询要有预算，也要能真正取消。**
采集周期、并发上限、服务端超时和熔断策略应该一起设计。
客户端放弃等待，不代表数据库里的查询已经停止。

**二、只采完成任务所需的最少信息。**
如果目标是分析锁等待，
MySQL 8.0.40 之后应优先评估
Performance Schema 的 `data_locks` 与 `data_lock_waits`。
如果确实需要 `INNODB_TRX` 的事务信息，
就要控制频率，并在目标负载下验证采集成本。

**三、探活要区分“慢”和“死”，切换后还要验收。**
单一探针连续失败只是信号，
不是完整诊断。
拉闸之前要确认备节点更健康，
拉闸之后要确认用户侧指标真的改善。

**四、整改至少需要三份证据。**
执行记录证明“做了”，
效果验证证明“生效了”，
客户回执证明“闭环了”。
少一份，都容易在下一次相似症状出现时重新争论。
